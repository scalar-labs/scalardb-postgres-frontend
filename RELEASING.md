# Releasing

A release publishes the engine to Maven Central, where a ScalarDB Cluster node depends on it.

## What gets published

| Artifact | Coordinate | Consumed by |
| --- | --- | --- |
| Engine | `com.scalar-labs:scalardb-postgres-frontend-engine` | ScalarDB Cluster nodes, which embed it |

With its sources and javadoc jars, under the Apache License 2.0 (`LICENSE`, also inside each jar).
`:server`, the standalone server, is not published to Maven Central: it ships as the fat jar and the
container image, and it compiles against the Cluster client SDK of the same version, which Cluster
releases after the engine it embeds.

Every commit on `main` and on a version branch also publishes the engine's `-SNAPSHOT` to the Maven
Central snapshot repository (`release-snapshot.yml`), so a Cluster build can track a line between
releases:

```kotlin
repositories {
    maven("https://central.sonatype.com/repository/maven-snapshots/")
}
dependencies {
    implementation("com.scalar-labs:scalardb-postgres-frontend-engine:3.20.0-SNAPSHOT")
}
```

## Branching model

The same as [ScalarDB](https://github.com/scalar-labs/scalardb): `main` is the trunk, a major version
branch carries the next minor release of an older major, and a release is tagged on its minor version
branch, never on `main`. The engine's version follows the ScalarDB version it is built against.

Once `3` and `3.20` are cut (below), the branches are:

| Branch | Carries | ScalarDB it builds against |
| --- | --- | --- |
| `main` | `4.0.0-SNAPSHOT` | `master`, `4.0.0-SNAPSHOT` |
| `3` | `3.21.0-SNAPSHOT` | `3`, the next 3.x |
| `3.20` | `3.20.1-SNAPSHOT` after `v3.20.0` | `3.20.0` |

Until then, only `main` exists, at `3.20.0-SNAPSHOT`.

Branch names carry no prefix. Every workflow matches them with the `[0-9]+` and `[0-9]+.[0-9]+`
patterns, so a branch such as `release/3.20` gets no CI and publishes no snapshot.

A change lands on `main` first and is then cherry-picked to the version branches that need it.
`main` is not merged into `3` once `main` has moved to the next major, since that would bring 4.0-only
changes into the 3.x line.

### Cutting a branch

A branch and its parent must never carry the same version: both would publish the same snapshot, and
`release-snapshot.yml` cannot tell which one is right. So the parent is bumped first, and the branch is
cut from the commit just before the bump.

To cut `3` from `main`, the first time:

1. On `main`, at `3.20.0-SNAPSHOT`: note the head commit, `C`.
2. On `main`: bump `version` in `gradle.properties` to `4.0.0-SNAPSHOT`, and `scalardb` and
   `scalardb-cluster` in `gradle/libs.versions.toml` to `4.0.0-SNAPSHOT`. Push.
3. Create `3` from `C` and push it. It publishes `3.20.0-SNAPSHOT`.

To cut `3.20` from `3`, when ScalarDB cuts its 3.20 line:

1. On `3`, at `3.20.0-SNAPSHOT`: collect the 3.20.0 changelog (see [When releasing](#when-releasing))
   and push it, then note the head commit, `C`. Batching here rather than on `main` takes in every
   fix cherry-picked to `3` since it was cut:

   ```bash
   changie batch v3.20.0
   # edit .changes/v3.20.0.md into release notes
   changie merge
   ```

2. On `3`: bump `version` to `3.21.0-SNAPSHOT`, and the ScalarDB versions to what ScalarDB's `3`
   branch publishes. Push.
3. Create `3.20` from `C` and push it. It publishes `3.20.0-SNAPSHOT`.

## Changelog

The same process as [ScalarDB Saga](https://github.com/scalar-labs/scalardb-saga/blob/main/RELEASING.md#changelog).
[CHANGELOG.md](CHANGELOG.md) and each GitHub release's notes are generated by
[changie](https://changie.dev) (`brew install changie`, `go install github.com/miniscruff/changie@latest`,
or `npm i -g changie`) from one entry file per change, configured in [.changie.yaml](.changie.yaml).
An entry is a file of its own, never an edit to `CHANGELOG.md`, because a backport is a cherry-pick: a
new file always applies cleanly to a release line, while an edit to `CHANGELOG.md` either conflicts there
or applies cleanly into a section that line has already released.

### Adding an entry

A change that users can see adds an entry in the same commit. Run this in the repository and commit
the file it writes:

```console
$ changie new
Kind: Improvements
Body: Text sorts and compares by code point, as ScalarDB 3.20 does.
Pull request number:
```

The same without prompts, as an agent runs it:

```bash
changie new --interactive=false --kind improvement \
  --body 'Text sorts and compares by code point, as ScalarDB 3.20 does.'
```

That writes `.changes/unreleased/improvement-<timestamp>.yaml`:

```yaml
kind: improvement
body: Text sorts and compares by code point, as ScalarDB 3.20 does.
time: 2026-10-29T14:30:05.123456+09:00
```

- **Kind** is `enhancement` (Enhancements: a new capability), `improvement` (Improvements: a change
  to existing behavior) or `bugfix` (Bug fixes). A change that is two kinds gets two entries.
- **Body** says what users see, not how the code changed, following the
  [Guidelines for Writing Release Notes](https://developers.scalar-labs.com/docs/style-guide/release-notes/).
  Start it with `[BREAKING]` when users have to change their code, configuration, or deployment.
  Name a file as code (`docs/user/clients.md`) rather than linking it: a relative link breaks in the
  GitHub release.
- **PR**, the pull request number, is rendered as a link after the body. Leave it empty for a
  commit pushed directly.

A change users cannot see the effect of (a refactor, tests, CI, documentation) adds no entry. A
backport needs nothing: the cherry-pick carries the entry file to the release line.

Changes are pushed to `main` directly for now, so nothing checks for an entry before it lands; a
malformed one fails `changie batch` at release. Once changes go through pull requests, they follow
Saga's rules: Conventional Commits titles, and the [Changelog](.github/workflows/changelog.yml)
workflow, which already runs on every pull request, fails a `feat:` or `fix:` one that adds no entry
and is not labelled `no-changelog`, and any pull request while a pending entry is malformed. Then
create the `no-changelog` label and make `entry` a required status check on `main` and the version
branches. Not before: a required check also refuses a direct push.

### When releasing

`changie batch` moves the pending entries into `.changes/v<version>.md` and deletes them, and
`changie merge` rebuilds `CHANGELOG.md` from the per-version files. Between the two, edit
`.changes/v<version>.md` into release notes: the entries were written one change at a time, so
combine those that describe one change and reword them to read as a whole.

- **A minor release** batches on the branch its release branch is cut from, before the cut: `main`
  until a major version branch exists, the major version branch after that (`3` for `3.20`). Entries
  reach a major version branch the way its code does, by cherry-pick, so that branch holds exactly
  the minor's entries, and the cut takes the batch along.
- **A major release** batches on `main`. `main` still holds its copies of every entry that shipped
  from the previous major version branch, since those reached that branch by cherry-pick, so drop
  them from the new major's notes while editing them. The batches on that branch deleted them, so
  `git log origin/<major> --diff-filter=D --name-only -- .changes/unreleased` lists them.
- **A patch release** batches on its release branch, in the commit that sets the version. It
  collects only what was cherry-picked. `main` keeps its own copies of those entries, so the next
  minor lists those fixes too, which is right for anyone upgrading from the previous minor.
- **A pre-release** (`-rc.1`) batches nothing: its GitHub release previews the pending entries.

`verify-version` refuses a release tag, before anything is published, unless
`.changes/v<version>.md` exists, lists at least one change, and no entry is left in
`.changes/unreleased/`. The GitHub release takes that file as its notes.

An entry left pending ships in the tagged release, so it belongs in that release's notes. It
happens when a fix reaches the release branch after its minor was batched, or when a patch
missed a late cherry-pick. `changie batch` refuses a version it has already written, so fold the
entries in by hand, on the release branch:

```bash
changie batch v<version> --dry-run   # prints the pending entries; nothing changes
# copy those bullets under their headings in .changes/v<version>.md
git rm .changes/unreleased/*.yaml
changie merge
```

Then move the tag to the new commit. Nothing was published from the refused one, since
`verify-version` runs before every other job, so it can simply be deleted and pushed again:

```bash
git tag -d v<version> && git push --delete origin v<version>
git switch <release-branch> && git pull
git tag -a v<version> -m "ScalarDB PostgreSQL frontend <version>" && git push origin v<version>
```

## Cutting a release

`release.yml` runs on a `v<major>.<minor>.<patch>` tag. It refuses a tag that does not match
`gradle.properties`, a `-SNAPSHOT` version, a commit that is not on the tag's minor version branch
(`3.20` for `v3.20.0`), and release notes that are missing or incomplete (see [When
releasing](#when-releasing)). It then uploads the engine to the Central Portal for someone to release,
and creates the GitHub release with `.changes/v3.20.0.md` as its notes.

### Steps

For `3.20.0`, on `3.20`:

1. Wait for ScalarDB `3.20.0` on Maven Central: the engine's POM depends on it.
2. Check `.changes/v3.20.0.md`: it carries the date `changie batch` ran, which is usually not the
   release date. Correct it and run `changie merge`, and fold in any entry still in
   `.changes/unreleased/` (see [When releasing](#when-releasing)). Cherry-pick that commit to `3`,
   which holds the same file, so that the two agree. For a patch, run `changie batch v3.20.1`, edit
   `.changes/v3.20.1.md` and run `changie merge` here instead; the file exists only on `3.20`.
3. Make the release commit: `version=3.20.0` in `gradle.properties` and `scalardb = "3.20.0"` in
   `gradle/libs.versions.toml` (`scalardb-cluster` stays a snapshot until Cluster releases). Push it and wait
   for CI.
4. Tag that commit and push the tag:

   ```sh
   git tag -a v3.20.0 -m "ScalarDB PostgreSQL frontend 3.20.0"
   git push origin v3.20.0
   ```

5. When `release.yml` has finished, open the deployment on the
   [Central Portal](https://central.sonatype.com/publishing/deployments). Once it has passed
   validation, check the files and select **Publish**. A published version cannot be replaced or
   withdrawn. It takes a while to appear on `repo1.maven.org`. The GitHub release exists already.
6. On `3.20`, bump `version` to `3.20.1-SNAPSHOT` and push, so that later snapshots from the branch do
   not reuse the released version.
7. In ScalarDB Cluster, change the engine dependency to `3.20.0`.

To re-run a release whose tag exists, for example after the upload failed, run `release.yml` by
`workflow_dispatch` with the tag selected as the ref. If only `github-release` failed, use **Re-run
failed jobs** on that run instead: a new run uploads again first, which Central refuses for a version
it already has, and `github-release` would never be reached.

A patch release is the same on the same branch: cherry-pick the fixes to `3.20`, then follow the steps
from 2 with `3.20.1`.

## Credentials

The workflows read four repository secrets, the same ones ScalarDB and ScalarDB Cluster use:

| Secret | What it is |
| --- | --- |
| `MAVEN_CENTRAL_USERNAME`, `MAVEN_CENTRAL_PASSWORD` | A Central Portal user token for the `com.scalar-labs` namespace |
| `MAVEN_CENTRAL_GPG_SECRET_KEY` | The ASCII-armored private key that signs the artifacts |
| `MAVEN_CENTRAL_GPG_PASSPHRASE` | Its passphrase |

A local `./gradlew publishToMavenLocal` needs none of them and publishes unsigned.
