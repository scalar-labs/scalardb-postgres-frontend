# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), with the section
names the ScalarDB family uses (Enhancements, Improvements, Bug fixes) instead of Keep a Changelog's
types. It is generated by [changie](https://changie.dev) from the files in `.changes/`; changes not
yet released are in `.changes/unreleased/`.

## [v3.20.1] - 2026-11-11

### Bug fixes

- A password is no longer repeated in an error message. `CREATE USER` or `ALTER USER` with a comment between its keywords, such as `CREATE /* note */ USER alice PASSWORD '...'`, was refused with an error that quoted the whole statement, password included, so a client that logs its errors could write the password to its log. Such statements now run like any other `CREATE USER`, and an error never quotes a statement that mentions a password.
- The container image runs the OpenJDK release that fixes CVE-2026-91403 and CVE-2026-114820.
- Fewer reads in transactions: when a statement reads rows that an earlier statement in the same transaction already read, such as a `SELECT` followed by an `UPDATE ... SET x = x + 1` of the same row, ScalarDB reuses the earlier read instead of reading the database again. In TPC-C this removes about 17% of the statements sent to the database. Because every read now fetches every column, `EXPLAIN` lists all of a table's columns in `projections=[...]`.
- Fewer reads for a join that looks up a table per row under an aggregate, sort or `DISTINCT`, which reads all of its rows anyway: its outer rows are read in batches of 128 from the start instead of growing from 16, so TPC-C StockLevel's stock lookups take two ScalarDB scans instead of four.
- Less CPU per statement and per row:
  - The settings reported to clients (ParameterStatus) are checked only after a statement that changed one, not after every statement. In a benchmark with prepared statements, that check was 7–9% of the frontend's CPU.
  - No regular expression runs on every statement to find its first keyword, read an integer parameter or look up a setting. In a TPC-C profile, this took the frontend's own share of its CPU from 44% to 33%.
  - A timestamp parameter in the form pgJDBC sends is read directly, and a float parameter is typed without an exception.
  - Rows convert only the columns the statement uses, column names and row keys are worked out once per statement, and a prepared statement's parameter count is kept from Parse instead of being counted at every Bind.
  - `client_min_messages` is read only when there are notices to send, `statement_timeout` is parsed once per value, and each protocol message is sent in one write.
- A statement's `OR` conditions keep the order they were written in when passed to ScalarDB, so the same statement always gives ScalarDB the same conditions.
- Built on ScalarDB 3.20.1. The container image ships the ScalarDB Cluster client SDK 3.20.0.
## [v3.20.0] - 2026-10-29

### Enhancements

- First release of the ScalarDB PostgreSQL frontend, a PostgreSQL-compatible SQL interface for ScalarDB. PostgreSQL clients and tools, such as psql, the PostgreSQL JDBC driver and ORMs, connect over the PostgreSQL wire protocol, and their SQL runs on the databases ScalarDB manages, as ScalarDB transactions: each statement outside `BEGIN` is one transaction, and `BEGIN ... COMMIT` is one transaction. It runs inside ScalarDB Cluster nodes (the recommended deployment) or as a standalone server on ScalarDB core. The engine is published to Maven Central as `com.scalar-labs:scalardb-postgres-frontend-engine`, which ScalarDB Cluster embeds. See `docs/user/README.md`, and `LIMITATIONS.md` for what the frontend refuses or does differently from PostgreSQL.
- SQL as PostgreSQL 16 answers it: queries with joins, subqueries, aggregates, window functions, set operations and CTEs; `INSERT`, `UPDATE`, `DELETE` and `INSERT ... ON CONFLICT` with `RETURNING`, also inside `WITH`; and table, index and schema DDL. Each query runs as far as possible in ScalarDB, and `EXPLAIN` shows how. See `docs/user/sql-reference.md`.
- Declared types keep PostgreSQL's rules: `NUMERIC(p,s)` is exact, `VARCHAR(n)`, `CHAR(n)` and `SMALLINT` are checked and shown as declared, and `json` and `jsonb` keep their type. The declarations are recorded in the frontend's metadata table, which `CREATE FRONTEND METADATA TABLES` creates once (see `docs/type-encoding.md`).
- Transactions run at the isolation level the ScalarDB deployment is set to, which `SHOW transaction_isolation` reports as PostgreSQL's closest level; a request for a stronger level fails rather than being ignored. See `docs/user/transactions.md`.
- `pg_catalog` and `information_schema` answer as PostgreSQL 16 does, or fail, so psql, pgjdbc, SQLAlchemy, Sequelize, Prisma and DBeaver read the schema. See `docs/user/clients.md` for the tested clients.
- Under ScalarDB Cluster: a password or an OIDC access token per connection, TLS, Cluster's users and privileges, encryption, and ABAC. See `docs/user/security.md`.
